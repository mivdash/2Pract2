# depviz

Инструмент визуализации графа зависимостей для NuGet-пакетов (.NET).
Зависимости получаются без менеджеров пакетов, напрямую из репозитория.

Практическая работа №2, вариант 7.

## Статус

| Этап | Описание | Готовность |
|---|---|---|
| 1 | Минимальный прототип с конфигурацией | готово |
| 2 | Сбор данных | готово |
| 3 | Основные операции (BFS без рекурсии, фильтр) | готово |
| 4 | Обратные зависимости | готово |
| 5 | Визуализация (Graphviz, PNG) | готово |

## Настройки

Параметры задаются в YAML-файле (по умолчанию `config.yaml`).

| Параметр | Тип | Описание |
|---|---|---|
| `package_name` | строка | Имя анализируемого пакета |
| `repository` | строка | URL репозитория (`http(s)://...`) или путь к файлу тестового репозитория |
| `test_mode` | true/false | Если `true`, `repository` считается путём к файлу |
| `output_image` | строка | Имя файла с картинкой графа, только `.png`, без пути |
| `ascii_tree` | true/false | Выводить зависимости в виде ASCII-дерева |
| `filter_substring` | строка | Пакеты с этой подстрокой в имени пропускаются, пустая строка отключает фильтр |

Все параметры обязательны. Лишние параметры считаются ошибкой.

Пример `config.yaml`:

```yaml
package_name: Newtonsoft.Json
repository: https://api.nuget.org/v3/index.json
test_mode: false
output_image: graph.png
ascii_tree: true
filter_substring: ""
```

## Что делает этап 1

Читает конфиг, проверяет все параметры и печатает их в формате `ключ: значение`
(вывод параметров нужен только на этом этапе, позже он убран).
При ошибке пишет сообщение в stderr и завершается с кодом 1.

Обрабатываемые ошибки: файл не найден, это папка, неверный YAML, пустой файл,
пропущенные параметры, неверный тип значения, пустое имя пакета,
неверный URL, отсутствующий файл тестового репозитория,
имя картинки не `.png`.

## Что делает этап 2

Берёт пакет из `package_name` и показывает его **прямые** зависимости.
Данные берутся напрямую из NuGet v3 API по адресу `repository`
(по умолчанию `https://api.nuget.org/v3/index.json`), без `dotnet`, `nuget`
и сторонних библиотек: только `urllib` и разбор JSON.

Как это работает:

1. Скачивается корневой документ `index.json` и в нём ищется ресурс
   `RegistrationsBaseUrl`.
2. По адресу `<registration>/<имя пакета строчными>/index.json` скачивается
   список версий. Если страница версий не вложена, она загружается отдельно.
3. Выбирается последняя стабильная (без `-beta`, `-rc` и т. п.) опубликованная
   версия. Если стабильных нет, берётся последняя предварительная.
4. Из `dependencyGroups` собираются зависимости. Группы для разных платформ
   (net8.0, netstandard2.0 и т. д.) объединяются без повторов.

Версия пакета в конфиге не задаётся, всегда берётся последняя.
Тестовый режим (`test_mode: true`) появится на этапе 3, пока он даёт ошибку.
Параметры конфига на этом этапе больше не печатаются, это нужно было
только на этапе 1.

На этапе 2 программа печатала только прямые зависимости, с этапа 3 печатается
полный граф (см. ниже). Формат вывода этапа 2 (имена и версии условные):

```
$ py -m depviz config.yaml
Пакет: Demo.Pkg 2.0.0
Прямые зависимости: 2
  Dep.One [1.0.0, )
  Dep.Two [2.1.0, 3.0.0)
```

Диапазон версий показан в записи NuGet: `[1.0.0, )` значит «1.0.0 и выше».

Ошибки: пакет не найден, сервер недоступен, неверный ответ сервера,
в репозитории нет нужного ресурса.

## Что делает этап 3

Строит граф зависимостей **с учётом транзитивности** и печатает его списком.

- Обход в ширину (BFS) через очередь `deque`, без рекурсии. Есть тест на
  цепочку из 5000 пакетов.
- Пакеты, в имени которых есть `filter_substring`, не учитываются: они не
  попадают в граф вместе со всеми связями. Регистр не важен. Если фильтру
  соответствует сам корневой пакет, выводится ошибка.
- Циклы (`A -> B -> A`) и зависимость пакета от самого себя не зацикливают
  обход: каждый пакет обрабатывается один раз, связь остаётся в графе.
- Если зависимость не найдена в репозитории, она остаётся листом графа.
  Неизвестный корневой пакет даёт ошибку.

Формат вывода списком (при `ascii_tree: false`):

```
Граф зависимостей пакета A (пакетов: 4)
A -> B, C
B -> D
C -> D
D -> (нет зависимостей)
```

### Тестовый режим

При `test_mode: true` параметр `repository` это путь к файлу, а не URL.
Пакеты названы заглавными латинскими буквами, одна строка описывает один пакет:

```
A: B C
B: D
C: D
D:
```

Слева от двоеточия пакет, справа его зависимости через пробел. Пустые строки
пропускаются. Ошибки в файле (нет двоеточия, строчные буквы, повтор пакета)
сообщаются с номером строки.

### Примеры

Готовые примеры лежат в папке `examples/`. Запуск из корня проекта:

```powershell
$env:PYTHONPATH="src"; py -m depviz examples/cycle.yaml
```

| Файл | Что показывает |
|---|---|
| `chain.yaml` | цепочка A, B, C |
| `diamond.yaml` | ромб: общий пакет D берётся один раз |
| `cycle.yaml` | цикл A, B, C, A |
| `filter.yaml` | ромб с фильтром `D`: пакет D исключён |
| `unknown.yaml` | ошибка: корневого пакета нет в файле |

Для настоящего NuGet полный граф большой: у `Newtonsoft.Json` через
`NETStandard.Library` набирается много пакетов, и сбор займёт время.
Чтобы сократить его, задайте фильтр, например `filter_substring: System`.

## Что делает этап 4

Режим `--reverse` показывает **обратные зависимости**: какие пакеты зависят
от `package_name`, напрямую или через другие пакеты.

```powershell
$env:PYTHONPATH="src"; py -m depviz --reverse examples/rev_diamond.yaml
```

Используется тот же обход BFS без рекурсии, что и на этапе 3: связи
разворачиваются (`reverse.py`), а `build_graph` остаётся прежним. Фильтр
`filter_substring` работает так же.

```
Обратные зависимости пакета D (пакетов: 4)
D <- B, C
B <- A
C <- A
A <- (никто не зависит)
Зависят от D: B, C, A
```

Строка `D <- B, C` читается как «от D зависят B и C».

**Ограничение.** Режим работает только с тестовым репозиторием
(`test_mode: true`). У NuGet нет запроса «кто использует пакет», узнать это
можно только перебрав все пакеты репозитория, поэтому для настоящего NuGet
программа выводит понятную ошибку.

Примеры в `examples/`:

| Файл | Что показывает |
|---|---|
| `rev_diamond.yaml` | у пакета D два пользователя, верхний пакет A один раз |
| `rev_chain.yaml` | цепочка вверх от C |
| `rev_top.yaml` | от верхнего пакета никто не зависит |
| `rev_cycle.yaml` | цикл не зацикливает обход |
| `rev_filter.yaml` | фильтр `B` убирает пакет B из результата |
| `rev_unknown.yaml` | ошибка: пакета нет в файле |

## Что делает этап 5

После построения графа программа:

1. Печатает зависимости: ASCII-деревом при `ascii_tree: true`, иначе списком
   из этапа 3.
2. Формирует описание графа на языке **Graphviz (DOT)** и сохраняет его
   рядом с картинкой (`graph.png` даёт `graph.dot`).
3. Сохраняет изображение **PNG** в файл `output_image`, вызвав программу
   `dot` из Graphviz.

Для картинки нужно установить [Graphviz](https://graphviz.org/download/)
и добавить его в `PATH` (в установщике для Windows есть такая галочка).
Проверка: `dot -V`. Если `dot` не найден, программа сообщит об этом, а
DOT-файл всё равно будет сохранён.

### ASCII-дерево

```
A
|-- B
|   `-- D
|       `-- E
`-- C
    `-- D (см. выше)
```

- Повторный пакет с зависимостями раскрывается один раз, дальше стоит
  пометка `(см. выше)`. Так дерево не разрастается на общих пакетах.
- Пакет, который уже есть выше по ветке, помечается `(цикл)` и не
  раскрывается: `A -> B -> C -> A`.
- Дерево строится рекурсивно, это разрешено заданием только для этапа 3.

### Описание Graphviz

```
digraph dependencies {
    rankdir=LR;
    "A" [style=filled, fillcolor=lightblue];
    "A" -> "B";
    "A" -> "C";
    "B" -> "D";
    "C" -> "D";
}
```

Корневой пакет выделен цветом, стрелка `A -> B` значит «A зависит от B».
Файлы `*.png` и `*.dot` внесены в `.gitignore`: это результат запуска, а не
исходный код.

### Примеры

Запуск:

```powershell
$env:PYTHONPATH="src"; py -m depviz examples/tree_shared.yaml
```

| Файл | Что показывает |
|---|---|
| `tree_shared.yaml` | дерево с общим пакетом D, пометка `(см. выше)` |
| `tree_cycle.yaml` | дерево с циклом, пометка `(цикл)` |
| `nuget_newtonsoft.yaml` | настоящий пакет `Newtonsoft.Json` |
| `nuget_logging.yaml` | настоящий пакет `Microsoft.Extensions.Logging` |
| `nuget_moq.yaml` | настоящий пакет `Moq` |

В конфигах настоящих пакетов стоит `filter_substring: System`: платформенные
пакеты `System.*` исключаются, иначе граф получается в несколько раз больше
и сбор занимает минуты. Чтобы увидеть полный граф, поставьте `""`.

### Сравнение со штатными инструментами

Штатные средства NuGet: страница пакета на nuget.org (раздел
Dependencies) и команда `dotnet list package --include-transitive`.
Для проверки:

```powershell
dotnet new console -o cmp
cd cmp
dotnet add package Newtonsoft.Json
dotnet list package --include-transitive
```

Сравнивать нужно набор пакетов в графе `depviz` и в выводе `dotnet`.
Расхождения возможны по таким причинам:

- **Выбор версии.** `depviz` берёт последнюю стабильную версию каждого
  пакета. NuGet при восстановлении берёт самую низкую версию, подходящую
  под диапазон: для `[4.3.0, )` это `4.3.0`. У разных версий один и тот же
  пакет может иметь разные зависимости.
- **Платформы.** Зависимости в NuGet сгруппированы по целевым платформам
  (`net8.0`, `netstandard2.0` и так далее). `depviz` объединяет все группы.
  `dotnet list` показывает только то, что нужно платформе проекта, а
  страница на nuget.org показывает группы по отдельности.
- **Фильтр.** При `filter_substring` часть пакетов намеренно исключена.
- **Конфликты версий.** `dotnet` выбирает одну версию пакета на весь проект
  и выводит плоский список с версиями. `depviz` версий не показывает и
  рисует связи между пакетами.
- **Предварительные версии.** `depviz` берёт предварительную версию только
  если стабильных нет.

Поэтому набор пакетов у `depviz` обычно **шире**, чем у `dotnet list`:
в нём собраны зависимости всех платформ.

## Установка, запуск, тесты

Нужны Python 3.10+ и (для картинок) Graphviz. Команды для Windows (PowerShell):

```powershell
py -m pip install -r requirements.txt
py -m pytest                                           # тесты
$env:PYTHONPATH="src"; py -m depviz config.yaml        # граф зависимостей
$env:PYTHONPATH="src"; py -m depviz --reverse examples/rev_diamond.yaml
```

Linux и macOS:

```bash
make install        # pip install -r requirements.txt
make run            # запуск с config.yaml
make run CONFIG=my.yaml
make test           # pytest -v
./run.sh examples/tree_shared.yaml
```

Ошибки печатаются в stderr со словом «Ошибка:», код завершения 1:

```
$ py -m depviz nope.yaml
Ошибка: Файл конфигурации не найден: nope.yaml
```
